# Feature Plan 2: Email & Password Authentication

> **Feature ID**: FP-02  
> **Feature Name**: Email & Password Authentication  
> **Status**: Planned (Awaiting Implementation)  
> **PRD Cross-Reference**: Feature F05 (`<MemberAuth>`), PRD Section 18 Conflict 6 ("Some buyers distrust OTP-only or SSO-only login")  
> **Priority**: Core Identity Parity Milestone  

---

## 1. Executive Summary & Market Context

While modern Framer plugins often push toward passwordless OTP and social SSO, market data from competitors (**FrameAuth**, **Thenty**, and **Outseta**) demonstrates that **Email + Password authentication is a mandatory baseline**:

* **Market Reality**: A significant segment of enterprise buyers, B2B clients, and privacy-conscious users distrust or reject OTP-only systems (due to corporate inbox spam filtering, email delivery delays, or security policies).
* **Parity Goal**: Provide a traditional, robust, and secure email + password authentication path inside `<MemberAuth>`, fully integrated with password reset workflows, account lockout protection, and zero code overrides.

---

## 2. User Flows & Experience

### 2.1. Member Registration Flow
1. Visitor navigates to the Framer site or clicks **"Sign in to unlock"** on a locked gate.
2. Inside `<MemberAuth>`, the visitor switches to the **Sign Up** tab.
3. Visitor inputs their **Email**, **Password** (with min 8-character validation and strength indicator), and optional **Name**.
4. Visitor clicks **"Create Account"**.
5. Backend hashes the password using Argon2id/bcrypt, creates the member record, sets an HTTP-only secure cookie, and fires an optional verification/welcome email.
6. The modal closes, `<MemberGate>` receives the session update, and gated content unlocks immediately.

### 2.2. Member Sign-In Flow
1. Visitor inputs registered **Email** and **Password**.
2. Optional checkbox: *"Remember me for 30 days"*.
3. Visitor clicks **"Sign In"**.
4. If credentials match -> HTTP-only session cookie is set, modal closes, and visitor is authenticated.
5. If invalid -> Displays inline field error: *"Invalid email or password. Please try again."* (Never reveals whether the email exists).

### 2.3. Password Reset Flow ("Forgot Password?")
1. Visitor clicks **"Forgot password?"** under the password input.
2. View transitions to the **Password Reset Request** screen.
3. Visitor enters their email and clicks **"Send Reset Link"**.
4. An email with a time-limited (15-minute), cryptographically signed token link is dispatched:  
   `https://yoursite.com/reset-password?token=...`
5. On the reset page, the visitor enters a new password and submits.
6. Existing sessions are invalidated, and the member logs in with the new password.

## 3. Architecture & Technical Design

### 3.1. Canvas Component Integration (`MemberAuth.tsx`)
In `src/canvas-components/MemberAuth.tsx`, extend the existing state machine:

```
                  ┌──────────────────────┐
                  │         IDLE         │
                  └──────────┬───────────┘
              ┌──────────────┴──────────────┐
              ▼                             ▼
       [Password Flow]                  [OTP Flow]
      /api/member/login-password     /api/member/send-otp
              │                             │
              ▼                             ▼
        [AUTHENTICATED] <─────────── [CODE_SENT]
     Set-Cookie HTTP-only            /api/member/verify-otp
```

#### State Machine Additions:
* Modes: `authMode: "password" | "otp"` (Creator-configurable or toggleable by visitor).
* Views: `signin`, `signup`, `forgot_password`, `reset_password_sent`.

### 3.2. Framer Property Controls
Add to `MemberAuth.tsx`:
```typescript
addPropertyControls(MemberAuth, {
  enablePasswordAuth: {
    type: ControlType.Boolean,
    title: "Password Auth",
    defaultValue: true,
  },
  defaultAuthMethod: {
    type: ControlType.Enum,
    title: "Default Method",
    options: ["password", "otp"],
    optionTitles: ["Email & Password", "Passwordless OTP"],
    defaultValue: "password",
    hidden: (props) => !props.enablePasswordAuth,
  },
  requirePasswordStrength: {
    type: ControlType.Boolean,
    title: "Strong Password",
    defaultValue: true,
    hidden: (props) => !props.enablePasswordAuth,
  },
});
```

### 3.3. Backend API Contract (External Dependency)
```
POST /api/member/register
Request:  { email, password, name, siteId }
Response: 200 { member: MemberSessionData } + Set-Cookie HTTP-only
          400 { reason: "weak_password" | "email_already_exists" }

POST /api/member/login-password
Request:  { email, password, rememberMe, siteId }
Response: 200 { member: MemberSessionData } + Set-Cookie HTTP-only
          401 { reason: "invalid_credentials" | "account_locked" }
          429 { reason: "rate_limited", retryAfterSeconds: 300 }

POST /api/member/forgot-password
Request:  { email, siteId }
Response: 200 { success: true } (Always returns 200 to prevent user enumeration)

POST /api/member/reset-password
Request:  { token, newPassword }
Response: 200 { success: true }
          400 { reason: "token_expired" | "invalid_token" }
```

### 3.4. Security Standards & Non-Negotiables
1. **Zero Client-Side Passwords**: Passwords are transmitted directly to the backend over HTTPS; no plaintext password is ever cached in state, `localStorage`, or session context.
2. **Brute Force Protection**: Account lockout after 5 consecutive failed password attempts for 15 minutes.
3. **No User Enumeration**: Login and password reset endpoints return identical generic timing-safe responses whether an email is registered or not.
4. **HTTP-Only Cookies**: Session tokens are strictly stored in `SameSite=Lax; Secure; HttpOnly` cookies.
