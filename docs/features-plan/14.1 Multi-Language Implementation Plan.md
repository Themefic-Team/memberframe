# FP-14 Multi-Language Support: Implementation Plan

> **Feature ID**: FP-14 (PRD F23, status task 7.5)
> **First release**: English, Spanish, French, German
> **Written**: 2026-10-27
> **Status**: Planned, not started
> **Spec**: [14. Multi-Language Support.md](14.%20Multi-Language%20Support.md)

---

## 1. Context

**Does MemberFrame have it today? Partly, not as a feature.**

| What exists | Where | Gap |
| :--- | :--- | :--- |
| Per-instance **Labels** group in Framer's sidebar (about 215 strings across 7 components), so a creator can retype every label by hand | `*_LABELS` maps, `mfLabel` and `mfLabelControls` in the shared appearance block of each `src/canvas-components/*.tsx` | Manual, per instance, per page. No real language support |
| `Site.defaultLocale` column (default `"en"`) | `memberframe-backend/prisma/schema.prisma:120`, selected in `src/middleware/site.ts` | Nothing reads it |
| Nothing | Errors, password hints, and similar (for example "Sign in was cancelled.", "Too weak") | Hardcoded English outside Labels |
| Nothing | Member emails (`memberframe-backend/src/lib/mailer.ts`, `services/payments/apply.ts:453`) | English only |
| Nothing | Checkout | No locale sent to the gateway |

### 1.1. Decisions (Product Owner, 2026-10-27)

- Ship **English, Spanish, French, German** first. English is the base and the fallback. More languages come later on the same system.
- A component shows the **language of the Framer page being viewed** (Framer Localization, for example `/es/`), else the **site language** chosen in MemberFrame Settings.
- Arabic is not in this release, so right-to-left layout is deferred.

### 1.2. Hard Constraints

- Each canvas component is one standalone file (imports only `react`, `react-dom`, `framer`, `lucide-react`), so dictionaries cannot be imported at runtime. They must be **baked in by the generator**.
- 40 kB gzipped budget per generated component (`test/memberAuth.test.ts`, "stays under the 40kB gzipped per-component limit"). Bake only the languages the creator picked.
- `mfLabelControls` sets each Label's `defaultValue` to the English text, so Framer passes English even when the creator typed nothing. The resolver must treat "equals the English default" as "not customized".

## 2. Approach

Resolution order for every string: the **creator's own Label text**, then the **translation for the active language**, then **English**. Never a raw key.

### L1. Shared Resolver (`// @memberframe-appearance-start` block, all 7 components)

- `mfLabel(labels, defaults, key, strings?)`: the creator's value when non-empty **and different from** `defaults[key][1]`; else `strings?.[key]`; else the English default. Existing callers keep working (no `strings` means today's behaviour).
- `mfActiveLocale(supported: string[], siteLocale: string): string`: reads the Framer runtime's locale hook if the `framer` module exposes one (guarded with `typeof`, never called if absent), else the primary subtag of `document.documentElement.lang` (Framer sets it per locale), else `siteLocale`. Only codes in `supported`. On the server (no `document`) it returns `siteLocale`. **Needs a check on a real Framer site** that `<html lang>` changes on `/es/` pages; the fallback is the site language.
- `mfFill` unchanged: `{name}` placeholders survive translation.
- `test/canvasAppearanceParity.test.ts` already proves the block is identical in every file. Extend its `mfLabel` cases: creator text wins, default-equal text falls through, a missing translation gives English.

### L2. Externalize Hardcoded Strings

- In each component, move visitor-facing literals that are not Labels (the error mapping in `MemberAuth.tsx` such as "Sign in was cancelled.", the password hints, "New sign ups are closed on this site.", and the equivalents in the other six) into a `*_MESSAGES: Record<string, string>` map, read through the same `t()`.
- Designer-only canvas notes ("Preview only. Sign in runs on your published site.", the popup's canvas chip) stay English: designers see them, visitors never do.
- Test per component: every `t("key")` key exists in `*_LABELS` or `*_MESSAGES` (read from source, as `test/authScreens.test.ts` already does for config keys).

### L3. Dictionaries (`src/locales/`)

- `src/locales/es.ts`, `fr.ts`, `de.ts`, each shaped `{ auth, dashboard, pricing, paywall, download, bookmarkButton, bookmarksTray }`. No `en.ts`: English stays in the component files, the single source the sidebar already shows.
- `src/locales/index.ts`: `SUPPORTED_LOCALES = ["en", "es", "fr", "de"]` with display names, and `stringsFor(namespace, locale)`.
- `test/localization.test.ts`: for every language and namespace, the keys equal the component's `LABELS` plus `MESSAGES` keys (parsed from source); every `{placeholder}` in English appears in the translation; no empty values; no em or en dashes (writing rule).
- Translations are drafted by the agent. **A native speaker must review es, fr, de before release** (recorded as human verification in `33-localization.md` section 7).

### L4. Generator (`src/services/canvasComponentCodeGenerator.ts`)

- `DeployContext` gains `siteLocale` and `locales` (the languages to include).
- Each config block gains `siteLocale` and `locales` fields (pattern: `authFields`). The key counts in `test/authScreens.test.ts` and its peers update.
- A new marked block `// @memberframe-strings-start` and `// @memberframe-strings-end` in each component, rewritten like the config block, holding `const MF_STRINGS: Record<string, Record<string, string>>` for the chosen non-English languages only.
- Size test: every generated component with all four languages stays under 40 kB gzipped (extend the existing Member Auth size test to each component).

### L5. Settings Language Card (`src/components/tabs/SettingsTab.tsx`, Config view) And Backend Setting

- A **Language** card built from kit components (`Field`, `Setting`, `SearchSelect`), respecting the one `.primary-cta` per view rule:
  - **Site language**: English, Spanish, French, German.
  - **Languages on your site**: a toggle each, prefilled from the Framer project's own locales via `framer.getLocales()` (plugin SDK, `node_modules/framer-plugin/dist/index.d.ts`), matched by code.
  - **Update components**: rewrites every MemberFrame code file in the project through the existing update path in `framerCanvasService.ts` (`setFileContent`), then shows a toast.
- Backend: saved into the site's settings (the `defaultLocale` column for the site language, a `locales` list in the settings document via `settingsService.ts`), validated against the supported list.

### L6. Dates And Money

- Every visible date and price in the components (Dashboard payments, Pricing cards, Bookmarks) formats with `Intl.DateTimeFormat` and `Intl.NumberFormat` using the active language. The plugin's `src/utils/money.ts` pattern is the reference.

### L7. Member Emails (Backend)

- Prisma migration: `Member.locale String? @db.VarChar(10)`.
- Components send `locale` (the active language) with sign up, sign in, code, and reset requests; the backend validates and stores it.
- `src/lib/mailer.ts`: subject and body strings for the sign-in code, confirm email, reset password, sign-in link, and password changed emails move to `src/lib/mailStrings/{en,es,fr,de}.ts`, and the continue email in `services/payments/apply.ts` too. Language: the member's locale, else `site.defaultLocale`, else English. Creator-facing mails (connect code, test email, billing) stay English.
- Tests: each mail renders in each language; an unknown locale gives English; the keys match across the four files.

### L8. Checkout, User Docs, QA

- The Pricing component sends `locale` to checkout. Stripe receives it as the session `locale` (es, fr, de are supported). Lemon Squeezy and Razorpay show their own default language: documented, not faked.
- User doc `user-docs/source/24-how-to-show-memberframe-in-your-language.md` (the Settings card, Framer Localization, overriding a Label, Update components), added to `user-docs/README.md` and rebuilt with `.agents/scripts/build-user-docs.cjs`.
- FP-14 and 7.5 rows move to `awaiting review`. PRD F23 acceptance criteria are ticked only where verified; the right-to-left one stays open, deferred with Arabic.

## 4. Out Of Scope (This Release)

- Arabic and right-to-left layout.
- Portuguese, Hindi, Japanese, Bengali. Each is added later as a new dictionary file, with no code change.
- The plugin panel's own UI (creators use Framer in English).
- Translating creator content such as tier names.
